# Core2A reasoning migration

Core2A teaches a learner to solve a **familiar question-family demand** by making the
application reasoning route explicit and supportable.

The current schema deliberately retains `answer.reasoning[]` and
`answer.difficult_move` for legacy compatibility. They are migration fallbacks, not the
forward authoring contract.

## Forward contract

Every new or materially revised Core2A-exposed question must use:

- `answer.reasoning_route[]` for explicit application reasoning state transitions;
- `answer.crux_move_ref` for the stable question-specific bottleneck;
- optional `question.scaffolds[]` targeted to reasoning-move ids;
- `answer.check` for learner-runnable result checking.

The Core2A crux may be a `REPRESENT`, `DECIDE`, `CONNECT` or `TRANSFORM` move when
that is the actual application bottleneck. It is not forced to be a model-choice
decision. A `VERIFY` move may close or test a route but is not the move that unlocks the
application.

Core2B remains stricter: `transfer.protected_move_ref` is the **changed learner
decision**, so it must still resolve to a `DECIDE` move.

## Inventory states

`Shared/tools/core2a_inventory.py` reports each Core2A-exposed canonical question as one
of:

- `STRUCTURED` — route and crux exist, the crux resolves, and its kind is a legitimate
  application bottleneck;
- `LEGACY_REASONING_MIGRATION_REQUIRED` — prose reasoning exists but structured
  application semantics have not been authored;
- `INVALID_PARTIAL_STRUCTURED_APPLICATION` — route/crux/scaffold migration was started
  but not completed coherently;
- `INVALID_DANGLING_CRUX` — the crux does not resolve inside the route;
- `INVALID_CRUX_KIND` — the crux is not an application bottleneck kind;
- `MISSING_APPLICATION_REASONING` — no usable application reasoning is present.

The report also records scaffold targeting, legacy difficult-move presence, learner-check
presence, figure count and move-level representation binding. Those are inventory facts,
not automatic pedagogical approval.

## Debt baseline

`docs/core2a-legacy-reasoning-baseline.json` is generated by:

```bash
python3 Shared/tools/core2a_inventory.py --write-baseline
```

The baseline is **not an acceptance list**. It freezes existing migration debt so CI can
distinguish old debt from newly created debt.

Guardrails run:

```bash
python3 Shared/tools/core2a_inventory.py --enforce-forward
```

The gate permits an unchanged legacy item to remain while its topic is migrated
deliberately. It refuses:

1. a new Core2A item that is not structured; and
2. a materially edited legacy Core2A item that still lacks a complete structured
   reasoning route/crux.

Once an item becomes `STRUCTURED`, it disappears from the debt set. Reverting it to
legacy form is therefore new debt and fails the gate.

## What counts as a material Core2A edit

The baseline digest covers learner-facing application semantics rather than provenance
metadata:

- stem, subparts, options and conditions;
- figures;
- primary/secondary capability and family binding;
- hints and pedagogical scaffolds;
- Core exposure;
- answer summary, prose reasoning, structured route/crux, legacy difficult move, check,
  subpart answers and rubric.

Source-custody metadata can evolve independently; changing the teaching/application
semantics cannot.

## Reasoning-quality and learner-check gate

The forward audit also rejects a deliberately narrow set of **mechanically falsifiable**
quality defects. It does not attempt to score pedagogy.

For structured reasoning routes it rejects:
- `why_valid` that merely repeats the move's `action`;
- `why_valid` that merely repeats the move's `output`;
- a small explicit set of generic justifications such as “because it works”;
- duplicate reasoning moves with the same action, justification and output.

Everything harder—whether the route exposes the *right* model connection, whether the
chosen crux is genuinely the learner bottleneck, whether the sequence is optimally
faded—remains a subject/pedagogy review judgment.

For `answer.check`, the audit distinguishes:
- `GENERIC_NON_EXECUTABLE`: “check your answer”, “redo the calculation”, etc.; these fail;
- `EXECUTABLE`: a check whose action matches a conservative known class such as
  substitution into the original condition, inverse/reversal, independent recomputation,
  limiting/special case, units/dimensions, sign/direction/bounds or representation
  cross-check;
- `EXECUTABLE_UNCLASSIFIED`: a concrete learner action that the generic audit does not
  classify confidently; this is allowed and remains subject-review material.

This prevents a keyword classifier from becoming a fake subject oracle. The machine blocks
only the obvious absence of an independent checking action.

## Representation binding

When an authored reasoning move or scaffold declares a canonical visual, the existing
`visual_support.py` and publication-boundary contracts already require the representation
and reveal stage to resolve together and belong to one another. Phase 2 therefore does not
create a second visual schema or a figure quota. Whether a representation is *needed* for
the application remains a pedagogical review question; when it is declared, its binding is
machine-checkable.

## Authoring rule

Core2A does **not** mean “generate the same question with different numbers or a new cover
story.” Select or author a familiar same-family application whose invariant demand and
decision structure remain unchanged. Surface variation is allowed, but synthetic
variation is neither required nor the purpose of the product.

Changing the demand belongs to Core2B and must satisfy the transfer contract.
