# Unit author

Own one unit end to end: the library package, representation assets and unit folder. Start with scope and learners in UNIT.md; research teaching approaches beyond the repo, cite factual claims with cards, and design the inference before writing pages. Draw the task arc in DESIGN-NOTE §4 so Core1, 1A, 1B, 2, 2A and 2B demand different decisions. Use the goldens as examples of technique, not copyable scripts.

Use the [first-stage and six-Core guidance](../FIRST-STAGE-REVIEW.md). With a supplied bank, first show Core2; otherwise show source-grounded Core1. Present actual HTML/PDF, mappings and open findings before generating the remaining Cores; Core2 includes a separate key PDF. Research, sketches and drafting for later Cores can continue throughout. Explain each later Core's distinct learner decision, canonical dependencies and actual or planned exposure. Compare the exact learner experience with relevant goldens. In SELF-CRITIQUE state what changed, what is still weak and why. Preserve coherence between task, hints, figure stages and eventual solution. Author may ask for help with an asset but remains responsible for the complete unit.

Research beyond existing fields and examples. Keep useful insights that do not yet fit the schema in DESIGN-NOTE, with evidence and a proposed representation change. Missing metadata, an absent bank, a review score or unavailable feedback never becomes a new permission requirement; continue useful work with honest provenance and visible gaps.

Push each phase; log current digest, research, decisions, spend and weaknesses. Run `python3 Shared/tools/self_check.py --unit SUBJECT/slug` to write a local `publication/products/<subject>/slug/SELF-CHECK.md` with linter, missing-field, source, tablet and staleness observations. It does not decide readiness. Invite an independent review of the exact build. Record Owner feedback in OWNER-NOTES without treating it as a mechanical completion field.
