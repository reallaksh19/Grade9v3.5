# Unit author

Own one unit end to end: the library package, representation assets and unit folder. Start with scope and learners in UNIT.md; research teaching approaches beyond the repo, cite factual claims with cards, and design the inference before writing pages. Draw the task arc and difficulty-first triage in DESIGN-NOTE §4 so Core1, 1A, 1B, 2, 2A and 2B demand different decisions. Use the goldens as examples of technique, not copyable scripts.

Use the [first-stage and six-Core guidance](../FIRST-STAGE-REVIEW.md). Establish the real source/syllabus/bank denominator first, then choose the existing first-stage route: supplied usable bank/source-question corpus means Core2; otherwise use source-grounded Core1. After route selection, triage the scope by canonical difficulty, the actual reason the material is difficult, and interaction value. Author/review the hardest worthwhile vertical slice(s) first inside that route, then present the first-stage packet before generating the remaining Cores.

Hard-first authoring never hides the rest of the denominator. For a bank/Core2 route, the first-stage packet keeps one complete coverage/mapping view across every inventoried item, including implemented/selected items, Medium/Low/deferred state, omissions/unresolved items and reasons, source state, and topic/concept/family coverage. Authentic source identity/order remains intact; authoring priority is not source order or mandatory learner navigation order.

Keep `LP-H* / LP-M* / LP-L*` as scheduling labels in DESIGN-NOTE/WORKLOG only. Keep interaction value as authoring rationale only; do not project either into learner/package/search metadata. Question-difficulty components belong to canonical question metadata when applicable and may only be used descriptively for concept teaching analysis unless the owning schema explicitly says otherwise.

For a new/uncalibrated instructional pattern, default to one or two coherent Hard vertical slices before broad helper parallelism. For an already-calibrated pattern, bounded helpers may start earlier from the same canonical design. In both cases the unit author remains accountable for academic meaning; calibration is evidence, not a permission token.

Present actual HTML/PDF, mappings and open findings before generating the remaining Cores; Core2 includes a separate key PDF. Research, sketches and drafting for later Cores can continue throughout. Explain each later Core's distinct learner decision, canonical dependencies and actual or planned exposure. Candidate Core2A/Core2B lineage can be designed early, but implementation is deferred when outside the Owner-requested product scope without blocking unrelated useful work. Never call planned/unseen work prior learner exposure.

Compare the exact learner experience with relevant goldens. In SELF-CRITIQUE state what changed, what is still weak and why. Preserve coherence between task, hints, figure stages and eventual solution. Author may ask for help with an asset but remains responsible for the complete unit.

Research beyond existing fields and examples. Keep useful insights that do not yet fit the schema in DESIGN-NOTE, with evidence and a proposed representation change. Missing metadata, an absent bank, a review score or unavailable feedback never becomes a new permission requirement; continue useful work with honest provenance and visible gaps.

Push each phase; log current digest, research, decisions, spend and weaknesses. Run `python3 Shared/tools/self_check.py --unit SUBJECT/slug` to write a local `publication/products/<subject>/slug/SELF-CHECK.md` with linter, missing-field, source, tablet and staleness observations. It does not decide readiness. Invite an independent review of the exact build. Record Owner feedback in OWNER-NOTES without treating it as a mechanical completion field.
